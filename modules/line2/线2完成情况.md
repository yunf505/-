## 4. 票03 的 6 红说明（同根因多处报出，非 bug）

fixtures/README §1 表格票03 期望"3 红"，实际引擎报出 **6 红**。**这不是 bug，是"同一根因，两处都会被报出，属正常"**（`README-接手先看.md §5-B` 原话）。

**3 组根因 × 每组 2 处报出 = 6 条**：

| 根因 | 数据 | 报出的 2 处 |
|---|---|---|
| 毛重差 12.73% | 发票 11000 vs 报关 9600 / 装箱 9600 | 报关↔发票、装箱↔发票 |
| 净重差 12.73% | 发票 9900 vs 报关 8640 / 装箱 8640 | 报关↔发票、装箱↔发票 |
| 身份冒用（同址不同名） | 发票 buyer「深港电子器件」 vs 报关 domestic_consignor / 装箱 buyer「东岸国际贸易」，raw_span 地址归一后均为「深圳市南山区科技园路88号3栋」 | 报关↔发票、装箱↔发票 |

fixtures/README §1 期望表的"3 红"是**按根因组数的简化写法**（明说"①报出 2 条：报关单↔发票、装箱单↔发票，同一根因；②1 条 CMP-IDENTITY"），未列净重的第 2 组根因和身份冒用的第 2 对组合，但数据里客观存在。

**未做去重的理由**（写进答辩稿）：
1. 去重需引入"选哪一条作代表"的主观判断，违反分工表硬约束①「判定必须是确定性规则」
2. `README-接手先看.md §5-B` 明确支持多处报出：「同一根因，两处都会被报出，属正常」
3. 每一对 doc 都是独立证据链，前端渲染时用户能一眼看出"发票是离群方"（3 组根因里发票都是那个"不一样的"）

## 6. 演示案例（票03 身份冒用，答辩现场用）

**这是 A 点名的两个负样本之一（E2「盗用身份报关（同址不同名）」），演示时最能体现"业务判断力"。**

**输入**：`03-输入/fixtures-synthetic/票03-主体不符-同址不同名/`（报关单 + 发票 + 装箱单）

**关键数据**：
- 报关单栏30 Importer of Record：`「东岸国际贸易（深圳）有限公司 / Add: 深圳市南山区科技园路88号3栋」`
- 发票 To：`「深港电子器件有限公司 / Add: 深圳市南山区科技园路 88 号 3 栋」`（注意"88 号 3 栋"多了空格）

**引擎判定链**（每一步都是确定性规则）：
1. **`addr_from_span`**（v1.1 §3.2）：从两侧 `raw_span.text` 正则抽 `Add:` 后的地址
2. **`norm_addr`**（阈值文档 §二）：NFKC + 小写 + 去全部空白 + 去标点 → 两侧都归一化为 `深圳市南山区科技园路88号3栋`
3. **地址相等** && **`norm_party` 主体名不等**（相似度远低于 0.85）
4. 触发 **`CMP-IDENTITY` → red**（不降级）
5. `message`：`买方疑似身份冒用：地址相同（归一化后「深圳市南山区科技园路88号3栋」）而主体名不同（commercial_invoice=「深港电子器件有限公司」 ↔ customs_declaration=「东岸国际贸易（深圳）有限公司」）`

**答辩话术**：
> 这就是 A 点名的负样本 E2「盗用身份报关（同址不同名）」。同样"名字不同"，**地址也不同只是普通差异**（走 `CMP-STR-PARTY`，判 red 或 orange），**地址相同才是冒用信号**（走 `CMP-IDENTITY`，固定 red，且不因低置信降级）—— 二者语义完全不同，引擎分开实现，不合并。

**现场演示命令**：
```bash
python compare.py "03-输入/fixtures-synthetic/票03-主体不符-同址不同名"
```

**配套演示**（README §G 已预告的两个必问问题）：

- **票01 的 0.40 美元**："你怎么证明 0.40 美元那条不是漏报？"
  → 答：这是我们设的金额相对容差（v1.1 §3.1 官方公式 `tol = max(1.00, 0.005×max|a,b|)`），依据是 CBP 存在整数舍入惯例（映射表 §6 原文：*7501 的 Entered Value 允许取整申报，逐分相等反而不真实*）。演示时可以临时把容差调成 0 复现一次，证明它确实被这套规则识别到了、只是被规则放过。
  → 现场复现命令：修改 `compare.py` 里 `amount_tol()` 返回 0，重跑票01，会看到 1 条 red；改回来又变绿。**判定可复现，是纯规则而非 LLM 的最好证明。**

- **票01/04/06 的 TO ORDER**："TO ORDER 为什么不报错？"
  → 答：这是国际贸易标准写法，已写入 `POL-TO-ORDER` 策略并记入 `skipped[]`，是有意为之而非遗漏。同时引擎自动改用 `notify_party` 作为旁证参与买方链比对（`get_field_meta` 里的特殊通道），所以不是"完全不比"，是"换个字段比"。

### B.3 如实回答

**"哪一档在实际六票里没被触发过？"**

- **第 3 档严格版（invoice_no + 三元组）作为 `group_key_type` 从未在六票里出现过**。原因：fixtures 里只有发票和装箱单有 `invoice_no` 字段（契约A v1.1 报关单和提单都没这个字段），且发票和装箱单必然先通过 `container_no`（第 1 档）合并，第 3 档严格版永远是"锦上添花"而非"决定归组"。

### B.4 潜在串票风险与防护

**风险 1**：`bl_no` 模糊匹配会串票
- 票04 提单 `SZPLA2400404` 与票06 提单 `SZPLA2400606` 的 SequenceMatcher ratio ≈ 0.92
- 若归组阶段用模糊匹配（≥0.70），两票会被错误合并
- **防护**：归组阶段 `bl_no` **只用严格相等**（`norm_id(a) == norm_id(b)`）；模糊匹配只在**比对阶段**用（判 OCR 噪声，如票01 的 E6 案例 ratio=0.769）

**风险 2**：金额+件数宽松匹配可能误归
- 若两票的金额和件数碰巧相同（例如两票小样品都是 100 件、总额 500 USD），会被误归
- **防护**：宽松版只在"一方无 invoice_no 且无 container_no 且无 bl_no"时才启用（`compare.py` 第 3 档宽松版的 `if not fj["invoice_no"] and fj["container_no"] is None and fj["bl_no"] is None: continue` 逻辑），且要求对方**至少有一个强键**，避免"三无文档"之间乱合并
- **未覆盖场景**：如果生产环境里同时有两票"金额+件数完全相同的三无报关单"，仍会串票。**标注为已知限制**

**风险 3**：同目录兜底可能把不同票合并
- 第 4 档"同目录只有一个多元素组时把孤立文档加入"，若一个目录里混放两票且都无强键，会全部合并成一组
- **防护**：第 4 档仅在"该目录内只有一个多元素组"时生效；若目录内已经分出多个组，孤立文档不会被强行归入任何一组，而是自成一组（`group_key_type=directory_name`），走查方能看到"这票是弱归组"
- **票07 验证**：即使两票混放同一目录，因发票有各自 container_no，第 1 档已正确分组，第 4 档不会误合并
